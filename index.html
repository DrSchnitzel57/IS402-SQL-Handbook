Four rules for every query

Tell Postgres the schema

Write schema.table every time, which always works, or set a default schema once.

FROM SalesOrdersExample.Products
-- or, once, above your first query:
SET search_path TO student;

Use the prefix when a file mixes schemas. A SET line resets if pgAdmin reconnects, and it goes above Q1, never under a question.

Names ignore case, values don't

Tables were created without quotes, so any capitalization of a name works. Never wrap names in double quotes.

Text values go in single quotes and must match exactly: 'WA' is not 'wa'. Numbers take no quotes.

Give tables short aliases

FROM SalesOrdersExample.Products AS p
-- then refer to p.ProductName

Once a table has an alias, use only the alias. It's required when two joined tables share a column name.

One query, one semicolon

Each question gets exactly one statement ending in ;. Leave out scratch queries, and don't edit the -- Q#: lines.

A missing semicolon makes Postgres read the next query as part of this one.

Run one query and read its row count

In pgAdmin's Query Tool, highlight one query and press F5 to run only that selection. The row count appears under the results grid and in the Messages tab. To get just the count, wrap the query:

SELECT COUNT(*)
FROM ( /* your query, without its semicolon */ ) AS t;

Look at a table before filtering on text

When a question filters on a value stored as text, look at the table first so your value matches its spelling, capitalization and format exactly. It also shows you whether a date column includes a time.

New to databases?

A database stores data in tables. Each row is one item, such as one customer, and each column is one fact about every item, such as the customer's city. Tables connect through keys.

TermMeaning
Primary key (PK)The column whose value is different in every row, like CustomerID. It identifies exactly one row.
Foreign key (FK)A column that stores another table's primary key. It's how an order records which customer placed it, and it's what you join on.
Linking tableA table keyed on two foreign keys that pairs rows from two other tables, like Order_Details pairing orders with products.
SchemaA named group of tables, like a folder. schema.table says exactly which table you mean.
NULLA missing value. It isn't zero or blank text, and it needs IS NULL to find.
AliasA short temporary name for a table or column, written with AS.

How tables relate

One-to-many is the most common relationship. One customer places many orders, but each order belongs to one customer, so the foreign key sits on the "many" side: Orders has a CustomerID column.

Many-to-many needs a linking table. An order holds many products, and a product appears on many orders, so Order_Details stores one row per product per order, with a foreign key to each side.

Planning a query

Six steps that turn any question into a query you can trust. Planning takes a minute; skipping it can cost twenty minutes of debugging.

  1. List the output.Write down every column the result shows, plus every column you'll filter or sort on.
  2. Find the tables.Open the database in Schemas and use "Find a column" to see which table holds each one.
  3. Trace the path.Connect those tables using the "Join on" list. If two tables share no column, look for a linking table between them.
  4. Name the shape.Decide what kind of question it is. Choosing the right tool lists the shapes.
  5. Build in layers.Write FROM and the joins and run it with SELECT *. Add WHERE and run it again. Then pick the final columns and add ORDER BY.
  6. Check.Compare the row count to the target, read down the sort order, and spot-check one row against the raw table.

Clause order and operators

You write clauses in one order, but Postgres runs them in another. The run order explains most of the errors you'll hit.

The order you write it

  1. SELECT [DISTINCT]
  2. FROM
  3. JOIN … ON
  4. WHERE
  5. GROUP BY
  6. HAVING
  7. ORDER BY
  8. LIMIT

The order Postgres runs it

  1. FROM and every JOIN
  2. WHERE
  3. GROUP BY
  4. HAVING
  5. SELECT
  6. DISTINCT
  7. ORDER BY
  8. LIMIT

What that means for you

  • WHERE checks one row at a time, before any totals exist. So WHERE price > AVG(price) is an error. Use a subquery, or HAVING for group totals.
  • WHERE runs before SELECT, so it can't use a column alias you made up in SELECT. ORDER BY runs last, so it can.
  • DISTINCT runs before ORDER BY, which is why Postgres requires every sort column in a SELECT DISTINCT query to also be in the select list.
  • LIMIT runs last, so ORDER BY decides which rows survive.

Filtering rows

WHERE

WHERE holds a test that's checked against every row. Rows where the test is true are kept; rows where it's false, or can't be decided because of a NULL, are dropped.

Syntax

SELECT columns
FROM schema.table
WHERE condition_1
  AND (condition_2 OR condition_3);

Examples

-- Members in Utah or Idaho
SELECT first_name, last_name, state
FROM members
WHERE state IN ('UT', 'ID');

Postgres applies AND before OR, the way multiplication comes before addition. Wrap the OR choices in parentheses so they're grouped the way you mean.

Use it when

  • The question limits the rows: a city, a price, a date range, a type.

Watch out

  • Text and dates go in single quotes and must match exactly: 'UT' is not 'ut'. Numbers take no quotes.
  • Double quotes mean a column name. WHERE state = "UT" fails with "column does not exist."
  • WHERE state = 'UT' AND city = 'Provo' OR city = 'Boise' keeps every Boise row in any state. Add parentheses.
  • BETWEEN includes both ends. For "more than 10 and less than 20," use > 10 AND < 20.

LIKE / ILIKE

LIKE compares text against a pattern. % stands for any number of characters, including none, and _ stands for exactly one. LIKE is case-sensitive; ILIKE ignores case.

Syntax

FROM schema.table
WHERE text_col LIKE 'pattern';

Examples

-- Titles that start with 'The'

Testing changes safely

INSERT, UPDATE and DELETE change stored data, and pgAdmin saves each change the moment it runs. Wrap a test in a transaction: BEGIN starts it, and ROLLBACK undoes everything since then. Use COMMIT instead to keep the change.

Check your work

Most assignments give a target row count. If yours doesn't match, start here.

Row count doesn't match

  • A join repeated your rows.Joining a "one" table to a "many" table repeats the "one" side once per match. If each thing should appear once, use IN or EXISTS instead of a join, or add DISTINCT.
  • A join is missing its ON condition, or compares the wrong columns.Every row pairs with every row. Counts in the hundreds or thousands give it away. A two-column key needs both columns in the ON.
  • DISTINCT is there but nothing collapsed.One of your selected columns differs between the copies. Remove any columns the question didn't ask for.
  • OR without parentheses.AND runs before OR. Wrap the OR choices so they're grouped the way you mean.
  • An extra GROUP BY column.Each extra column splits the groups further. Group only by what the question says "per".
  • UNION ALL instead of UNION.UNION ALL keeps duplicates.
  • "Never" written as "not equal".<> finds rows that did something else. To find rows that never did the thing, use NOT IN or NOT EXISTS.
  • An inner join dropped unmatched rows.If rows without a match must appear, use a LEFT JOIN with the keep-everything table first.
  • A later inner join undid the outer join.After the first LEFT JOIN on a path, every join that follows must also be LEFT.
  • A WHERE condition on the outer-joined table.It removes the NULL rows. Move the condition into ON.
  • > where you needed >=."At least" includes the boundary.
  • A range that ends too early.Text sorts in dictionary order, so "Wilson" comes after "W". A month of timestamps ends before the first of the next month, not at the 31st.
  • UNION removed duplicates.Use UNION ALL if repeated rows should stay.
  • An extra table in the join.Every inner join is also a filter. Remove tables the question doesn't need.
  • A value that matches nothing.Wrong capitalization, a stray space, or a code where the table stores a description (or the reverse). Look at the table first.
  • A timestamp compared with a plain date.A plain date means midnight. Compare col::date instead. See Dates and times.
  • = NULL instead of IS NULL.Nothing equals NULL, not even NULL. Also check whether blanks are stored as ''.
  • NOT IN with a NULL in the subquery.Add WHERE col IS NOT NULL inside the subquery, or switch to NOT EXISTS.
  • LIKE without a wildcard.LIKE 'The' only matches text that is exactly "The". Add %.
  • Conditions that can't both be true.AND where you meant OR, or a comparison pointing the wrong way.
  • DESC in the wrong place, or missing.DESC applies only to the column right before it.
  • No tie-breaker.Rows that tie on the first sort column come back in any order. Add the second column the question names.
  • The wrong sort column.First name instead of last name, a combined full name instead of the real columns, or an ID instead of a name.
  • Sort columns in the wrong priority.The first ORDER BY column wins; the second only sorts within ties.
  • NULLs at the bottom.That's expected. Postgres puts NULLs last when sorting ascending.

Find the line that causes it

  1. Check the joins alone.Replace your column list with COUNT(*) and remove WHERE. The count should make sense for the tables you joined.
  2. Add conditions back one at a time.Run after each one and watch which condition changes the count unexpectedly.
  3. Add grouping last.Put back GROUP BY or DISTINCT after the filters look right.
  4. Look at the real values.SELECT DISTINCT col FROM t ORDER BY col; often shows a spelling, capitalization or time-of-day surprise.

Error messages

The first line says what went wrong, and the ^ under your query marks where Postgres gave up. The real mistake is often just before that spot.

  • relation "…" does not existMissing schema prefix, a typo in the table name (Class_Rooms has an underscore), a name in double quotes, or a Query Tool connected to postgres instead of IS402Databases.
  • column "…" does not existA typo, the wrong table, a SELECT alias used in WHERE, or a text value in double quotes instead of single quotes.
  • column reference "…" is ambiguousTwo joined tables both have that column. Prefix it with an alias.
  • missing FROM-clause entry for table "…"You aliased a table but used its full name, or used an alias you never defined.
  • cross-database references are not implementedAn extra dot. Sales.OrdersExample.Orders reads as database.schema.table; write SalesOrdersExample.Orders.
  • syntax error at or near "…"Look just before that word: a missing comma or quote, a comma right before FROM, clauses out of order, or a missing semicolon on the previous query.
  • unterminated quoted stringA single quote was never closed. For an apostrophe inside text, type two: 'O''Brien'.
  • operator does not exist: numeric ~~ unknownLIKE on a number column. Use BETWEEN or >= and < instead.
  • operator does not exist: character varying = integerA text column compared with an unquoted number. Quote it: zip = '10025'.
  • invalid input syntax for type …A value that can't be read as that type, like text compared with a number column, or a date not written 'YYYY-MM-DD'.
  • function round(real, integer) does not existRounding to decimal places needs a numeric value: ROUND(col::numeric, 2).
  • column "…" must appear in the GROUP BY clause or be used in an aggregate functionYou mixed an aggregate with plain columns. Add the column to GROUP BY, or find the value in a subquery.
  • aggregate functions are not allowed in WHEREMove the aggregate into a subquery, or into HAVING for group totals.
  • window functions are not allowed in WHERECalculate it in a WITH step, then filter outside.
  • more than one row returned by a subquery used as an expressionA subquery after =, > or < returned several rows. Use an aggregate, or IN if you meant "is in this list".
  • subquery has too many columnsA subquery after IN must select exactly one column.
  • each UNION query must have the same number of columnsCount the columns in both halves.
  • for SELECT DISTINCT, ORDER BY expressions must appear in select listAdd the sort column to SELECT, or avoid duplicates another way.
  • division by zeroDivide by NULLIF(y, 0) to get NULL instead of an error.
  • date/time field value out of rangeAn impossible date like '2017-02-30', or a date not written 'YYYY-MM-DD'.
  • duplicate key value violates unique constraintAn INSERT used a primary key that already exists.
  • null value in column "…" violates not-null constraintAn INSERT left out a required column.
  • update or delete on table "…" violates foreign key constraintOther rows still point to the row you're deleting. Delete the child rows first.
  • insert or update on table "…" violates foreign key constraintThe new value points to a row that doesn't exist. Insert the parent row first.
  • INSERT has more expressions than target columnsThe VALUES list is longer than the column list. Match them one to one.
  • current transaction is aborted, commands ignored until end of transaction blockA statement inside BEGIN failed. Run ROLLBACK; and start again.
